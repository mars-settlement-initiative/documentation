Exercise 2: investigate prompt-driven decisions
================================================

**Working folder:** ``mars_colony_3``. **Edit:** only the strategy section below
``CHALLENGE 2: STUDENTS MAY EDIT THE STRATEGY BELOW`` in ``prompt.txt``.
Investigate whether a prompt produces useful collector decisions and how those
decisions affect interactions and colony survival.

What changes from Exercise 1?
-----------------------------

The world, Mesa activation, consumption and physical mechanics remain the same.
Explorers retain their original rules. Collector turns still begin with
collection, unloading and recharge, but their decision block now follows:

.. code-block:: text

   create_observation()
       -> continue a valid journey or request a decision
       -> validate the decision or use fallback rules
       -> execute one action using the existing mechanics
       -> record the prompt, source, decision and outcome

The supplied implementation adds the following components for you to read:

.. list-table:: Code supplied for Exercise 2
   :header-rows: 1

   * - File
     - Responsibility
   * - ``agents.py``
     - Builds collector observations and executes actions;
       ``baseline_step()`` preserves the original policy as a reference.
   * - ``model.py``
     - Makes one shared decision engine available to all collectors.
   * - ``llm_decision.py``
     - Routes and validates decisions, continues journeys, applies fallback,
       classifies failures and records JSONL/CSV decision logs.
   * - ``gemini_client.py`` / ``llm_config.py``
     - Gemini requests, structured output, model, pacing, cadence, timeout and
       call-limit settings.
   * - ``prompt.txt``
     - Instructions for one collector; its strategy section is the student edit
       area.
   * - ``app.py``
     - Shows the simulation and a full-width prompt/decision log in Solara.
   * - ``metrics.py``, ``analysis.py``, ``benchmark_worker.py``
     - Measure the actual code in all three folders, show live benchmark request
       progress and save matched-seed comparisons.

This is a hybrid agent. An LLM can guide eligible collector choices, while
fixed rules handle forced actions and the simulation mechanics. It does not
control the whole colony or rewrite Python. Folder 2 student changes are not
inherited by Folder 3; the comparison tool nevertheless runs the actual code in
each folder. Disclose any Folder 2 explorer changes when interpreting results.

Information and allowed actions
-------------------------------

The observation includes the collector's position, energy, cargo, capacity,
base location, known deposits, remembered target, other active collectors'
shared targets and the decision interval. Undiscovered locations and deposit
quantities are withheld. A remembered target can be depleted. Shared targets
indicate intentions; they do not reserve a deposit.

``COLLECT_x_y``
   Select a permitted target and move one cell toward it, horizontally first.
   Collection occurs through the existing mechanics at the beginning of a later
   collector turn after arrival.

``RETURN_BASE``
   Move one cell toward base. A loaded collector has this as its only allowed
   action, so no API request is needed for that forced choice.

``WAIT``
   Stay still without movement energy cost and retain target memory. The base
   still consumes supplies, so waiting is not free at the system level.

Every generated action is checked against ``allowed_actions``. Invalid or
unavailable responses use the baseline policy for that decision. A valid but
poor choice can still harm performance. One model tick does not imply one API
call.

Decision sources and counters
-----------------------------

The dashboard and logs distinguish how each choice was made:

.. list-table:: Per-turn decision sources
   :header-rows: 1

   * - Source
     - Meaning
   * - ``llm``
     - A new API response passed JSON and action validation.
   * - ``continued_llm``
     - A previous valid ``COLLECT`` or ``RETURN_BASE`` journey was reused.
   * - ``forced_action``
     - Only one action was available, so no API request was necessary.
   * - ``fallback``
     - The coded baseline policy handled a failed request, disabled provider or
       exhausted local call budget.
   * - ``mock_rules``
     - Offline demonstration using coded rules; no LLM was used.

``api_calls`` counts attempted provider requests. ``llm_decisions`` counts new
valid responses. ``continued_llm_decisions`` counts turns reusing a valid
journey. ``fallback_decisions`` counts turns controlled by the backup policy.
Inspect all four before attributing a result to the prompt.

The observational metrics include:

``idle_collector_steps``
   Active-at-start collector turns in which recorded movement did not increase.

``duplicate_target_steps``
   Extra active empty collectors sharing a still-known target after each tick.
   Three collectors targeting one deposit add two for that tick.

Request behavior and current defaults
-------------------------------------

The current defaults in ``llm_config.py`` are:

* Gemini model: ``gemini-3.1-flash-lite``.
* Local API-call ceiling: 120 attempts per simulation, shared by collectors.
* Request spacing: 1 second between completed requests.
* Journey reconsideration interval: 10 simulation ticks.
* Provider timeout: 20 seconds per request.
* Output ceiling: 1,024 tokens, with minimal Gemini thinking requested.

These are local experiment settings, not statements about provider quotas.
Keep the model, cadence, pacing and call ceiling identical when comparing prompt
variants. They can be overridden for a terminal session:

.. code-block:: powershell

   $env:GEMINI_MODEL = 'gemini-3.1-flash-lite'
   $env:MARS_MAX_API_CALLS = '120'
   $env:MARS_GEMINI_REQUEST_SECONDS = '1'
   $env:MARS_GEMINI_DECISION_INTERVAL = '10'

``COLLECT`` and ``RETURN_BASE`` choices can continue without another request.
Movement still occurs one cell per tick. Arrival, target depletion, low energy,
an unavailable action or cadence expiry causes reconsideration. ``WAIT`` is
reconsidered on the next turn. Turns with one allowed action do not call the
provider.

The simulation is synchronous: an eligible collector waits for its API response
before executing its action. The dashboard resumes as soon as the response
arrives. Request spacing, when nonzero, also uses wall-clock time and does not
advance the simulation or consume simulated resources.

Failure and fallback behavior
-----------------------------

A temporary failure affects the current decision only. The baseline policy is
used for that turn and a later eligible decision may call the provider again.
Temporary failures include timeouts, connection failures, service errors,
truncated output, invalid JSON and invalid generated decisions.

Failures that cannot be repaired by immediately repeating the same request
disable the provider for the remainder of the run. These include an invalid or
rejected key, denied access, an unavailable model, a rejected request, exhausted
quota and an invalid model name. Reaching the local call ceiling also routes new
choices to fallback. Restarting the simulation resets the local engine and call
budget, but does not reset provider quotas.

The terminal states whether future calls remain enabled:

.. code-block:: text

   LLM fallback: Gemini request timed out. Future API calls remain enabled.
   LLM fallback: Gemini API key was rejected. Further API calls are disabled for this run.

Start offline
-------------

From the student project root:

.. code-block:: powershell

   ./.venv/Scripts/python.exe mars_colony_3/run.py --batch --mode mock --seed 42
   ./.venv/Scripts/python.exe mars_colony_3/run.py --mode mock --port 8767

Mock mode demonstrates the observation/action interface and logging without
credentials. It uses coded rules, not an LLM. Editing the prompt cannot affect a
mock run. If live access is unavailable, report a revised prompt as an untested
hypothesis and label offline results clearly.

Run a live experiment
---------------------

Use the course-provided setup instructions in ``mars_colony_3/README.md``. The
launcher requests a key without writing it to the project:

.. code-block:: powershell

   ./mars_colony_3/gemini_setup.ps1

For a terminal experiment, set the key for that terminal and run a short trace:

.. code-block:: powershell

   $env:GEMINI_API_KEY = [System.Net.NetworkCredential]::new('', (Read-Host 'Gemini API key' -AsSecureString)).Password
   ./.venv/Scripts/python.exe mars_colony_3/run.py --batch --mode gemini --seed 42 --steps 50 --max-calls 10 --request-seconds 1

or in Command Prompt (CMD)

.. code-block:: bash

    set GEMINI_API_KEY=your-api-key
   ./.venv/Scripts/python.exe mars_colony_3/run.py --batch --mode gemini --seed 42 --steps 50 --max-calls 10 --request-seconds 1

An api key can be obtained at https://aistudio.google.com/api-keys

Keep keys out of prompts, logs and submitted files. Account access, billing and
quotas are provider settings; the code cannot select or verify an account tier.
The short run above is for inspecting decisions, not the full benchmark.

For the interactive dashboard with the same explicit pacing:

.. code-block:: powershell

   ./.venv/Scripts/python.exe mars_colony_3/run.py --mode gemini --port 8767 --request-seconds 1

To remove deliberate pacing and wait only for each real API response, use
``--request-seconds 0``:

.. code-block:: powershell

   ./.venv/Scripts/python.exe mars_colony_3/run.py --batch --mode gemini --seed 42 --steps 50 --max-calls 10 --request-seconds 0

Zero spacing is faster but may encounter provider rate limits. Changing request
spacing changes wall-clock duration, not simulation time. Use the same value for
every prompt variant in a controlled comparison.

Use the Solara evidence
-----------------------

The interactive dashboard includes a full-width **Agent prompts and decisions**
panel on its second row, with the three graphs beneath it. It displays the
system prompt and the 200 most recent decision records, newest first. Columns
include step, agent, whether an API call occurred, decision source, action,
reason, API reply, error, elapsed seconds and the observation prompt.

The **API reply** column contains only the returned ``action`` and ``reason``
JSON for new valid ``llm`` decisions. It is empty for continued, forced,
fallback and mock decisions because those rows did not receive a new valid API
decision.

Interactive decisions are appended immediately to the timestamped CSV path
printed by the launcher and displayed in the panel. The path normally has this
form:

.. code-block:: text

   mars_colony_3/results/<timestamp>/decisions.csv

Requirements and workflow
--------------------------

#. Run the offline demonstration and trace one observation, action and outcome.
#. Run the supplied prompt in live mode and save it as the prompt baseline.
#. Write: "If we change ___ in the strategy prompt, we expect ___ because ___."
#. Preserve the observation/action contract and edit only the strategy section
   in ``prompt.txt``.
#. Start a fresh live run with the same seed, model, cadence, pacing and call
   ceiling. Save it separately.
#. Inspect API replies, sources, errors and fallback counts before attributing
   an outcome to the LLM.
#. Compare matched seeds and connect an individual decision to an interaction
   pattern and colony-level outcome.

Compare separate repositories
-----------------------------

Each exercise repository contains a self-contained ``analysis.py``. Run it
inside that repository; the other repositories do not need to be installed or
present. Give each implementation a clear label:

.. code-block:: powershell

   # Run in the Folder 1 repository
   ./.venv/Scripts/python.exe analysis.py --label folder_1_baseline

   # Run in the Folder 2 repository
   ./.venv/Scripts/python.exe analysis.py --label folder_2_student_rules

   # Run in the Folder 3 repository
   ./.venv/Scripts/python.exe analysis.py --mode gemini --max-calls 120 --request-seconds 1 --label folder_3_prompt

All three scripts evaluate seeds 10, 20, 30, 40 and 50 for up to 500 ticks by
default. They print the same outcome table and write ``benchmark.csv`` with the
same columns. Download or copy the three CSV files and append their rows in
Excel, LibreOffice Calc or Google Sheets. The ``implementation`` column keeps
the rows identifiable after they are combined. ``summary.csv`` uses the same
four-column format in every repository: implementation, metric, mean and sample
standard deviation.

Live benchmarks print every Folder 3 API request as it starts. They also print
the maximum delay implied by request spacing. At 120 calls and one-second
spacing, pacing adds at most about 2 minutes per seed, plus provider response
time. A quick pipeline check is:

.. code-block:: powershell

   ./.venv/Scripts/python.exe analysis.py --mode mock --seeds 10 --steps 50 --max-calls 10 --label folder_3_mock

For a small live pilot:

.. code-block:: powershell

   ./.venv/Scripts/python.exe analysis.py --mode gemini --seeds 10 --steps 50 --max-calls 10 --request-seconds 1 --label folder_3_prompt

For the fastest benchmark, remove the deliberate delay:

.. code-block:: powershell

   ./.venv/Scripts/python.exe analysis.py --mode gemini --request-seconds 0 --label folder_3_prompt

Reducing ``--max-calls`` can shorten a run further, but after that ceiling the
fallback policy controls new decisions. This changes how much of the experiment
is LLM-driven. Reducing only ``--request-seconds`` preserves the call budget and
decision cadence unless rate limiting causes provider failures.

Folder 1 and Folder 2 write ``benchmark.csv`` and ``summary.csv``. Folder 3 also
writes ``benchmark.json``, the actual prompt, and per-seed JSONL and CSV decision
logs. Calculate paired differences after combining the exported tables by
matching rows on ``seed``; do not compare unrelated seeds.

Interpret the experiment
------------------------

Common metrics are:

* ``steps_survived``: ticks executed, including the depletion tick.
* ``resources_collected``: resources delivered to base, excluding carried cargo.
* ``distance_travelled``: recorded movement and therefore movement-energy use.
* ``failed_robots``: robots inactive at the end.
* ``idle_collector_steps``: active collector turns without movement.
* ``duplicate_target_steps``: overlapping collector intentions over time.

A plausible generated explanation is not evidence that the explanation caused
the outcome. Use the observation, allowed actions, executed source, subsequent
interaction and matched-seed results. Live outputs can vary even with the same
seed, so repeat important comparisons.

A successful investigation need not beat the baseline on every seed. It must
show that the implementation matches the hypothesis and that conclusions follow
from recorded decisions and repeated comparisons.

Completion checklist
--------------------

* Original and revised strategy prompts, with a hypothesis and explanation.
* Results for matched seeds, including Folder 1 and the actual Folder 2 rules.
* Provider/model, cadence, pacing, call limit, API attempts, valid LLM choices,
  continued choices and fallback counts.
* One traced observation -> API reply/source -> action -> interaction -> colony
  outcome.
* Means and spread across repeated matched seeds.
* A limitation or counterexample and a proposed next experiment.
